epoll이 사용됙 된 이유

epoll 은 리눅스에서 고성능 네트워크 서버를 위해 기존 I/O multiplexing 방식의
한계를 해결하기 위해 등장.

핵심은 많은 파일 디스크립터를 효율적으로 감시 하는 것.

## 1. 기존 방식의 문제점

(1) select
- FD 개수 제한: 보통 1024개 (FD_SETSIZE)
- 매 호출마다:
	- 사용자 -> 커널로 FD집합 복사
	- 커널 -> 사용자로 결과 복사
- 모든 FD 를 선형 탐색 O(n)

-> FD 많아질수록 성능이 급격히 하락함

(2) poll
- FD 개수 제한 없음 (동적 배열)
- 하지만 여전히:
	- 매번 전체 FD 리스트 전달
	- 매번 전체 순회 -> O(n)

FD 개수 제한이 있는 select 보다 낫지만 근본적인 해결 은 아님

## 2. 문제의 본질

대규모 서버에서 상황은 이렇다:
- FD 10,000개 중
- 실제 이벤트 발생은 10개

그런데도:
- select/poll -> 10,000 개 전부 검사
- 실제 이벤트가 일어난 FD는 몇개 없음

-> 비효율적 구조

## 3. epoll의 등장 목적
epoll은 이 문제를 해결하기 위해 설계됨

핵심 목표
1. FD를 매번 넘기지 않기
2. 이벤트가 발생한 FD 만 반환
3. O(1) 수준의 성능을 유지

# 4. epoll의 구조적 차이
(1) 관심 FD를 "등록"하는 방식
```
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, &event);
```

- 커널 내부에 FD를 저장
- 이후 반복 전달을 할 필요 없음

(2) 이벤트 발생만 전달
```
epoll_wait(epfd, events, maxevents, timeout);
```
- "준비된 FD만" 반환
- 불필요한 FD검사 없음

(3) 내부 구조
- 커널 내부:
	- Red-Black Tree -> FD 관리
	- Ready List (Linked List) -> 이벤트 발생 FD

-> 이벤트 기반 (push 방식)

## 6. 왜 epoll이 중요한가
다음과 같은 시스템에서 필수: \
	- 고성능 웹 서버 (Nginx) \
	- 채팅 서버 \
	- 게임 서버 \
	- 실시간 스트리밍 서버

"수만 개 연결"을 효율적으로 처리 가능

## 7. 한 줄 정리

epoll은 “모든 FD를 매번 검사하는 방식(select/poll)”을 버리고
“이벤트가 발생한 FD만 알려주는 방식”으로 전환하기 위해 탄생했다.
